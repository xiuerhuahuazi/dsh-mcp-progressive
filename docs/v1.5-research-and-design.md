## 二、差异点：我们真正不一样在哪

1. **加载是跨轮的，不是按轮的。** 我们 `mcp_load` 之后，工具在**本会话**里保持原生可见；`dsh-mcp-lazy` 默认本轮结束就收回（`releaseOnTurnEnd: true`）。
2. **我们给模型的是"可发现的目录"，不是"一个黑盒路由"。** 目录行让模型先知道有哪些 server、各有几个工具；路由式方案在冷态只有一个工具名，发现完全依赖那一次路由调用。
3. **披露 + 管理是一体的。** 面板能启停/重启/看实时状态；`dsh-mcp-lazy` 明确写了不管理第三方进程。1.4 的启动安全阀（starting 时禁用 Stop/Restart，避免 stdio dispose 的 SIGTERM 打到整个进程组）是这一类插件里目前只有我们有的东西。
4. **我们缺"连接层懒加载"。** 这是 `dsh-mcp-lazy` 比我们强的一处：工具说明藏了，但 MCP 进程还在。对不常用的 server，这是内存与启动成本。
5. **我们缺"省了多少"的可见数字。** `dsh-mcp-lazy` 给了分级测量；我们只有一次快照，没有账单数据。
6. **代码模式不是当前重点。** Anthropic 的 98.7% 依赖"用代码调工具 + 中间结果不进上下文"，收益最大但需要沙箱；DSH 有 `ptc-runtime`，但把它接进 MCP 披露是另一个量级的工程，先不做。

## 三、可容纳清单（按目标）

### 3.1 更省

| 项 | 吸收自 | 做法 | 风险 |
|---|---|---|---|
| P0 隐藏足迹可见 | dsh-mcp-lazy 的测量思路 | `mcp_servers` 返回每个 server 的 `hiddenTools` 与估算 `hiddenBytes/tokens`；面板每张卡显示「隐藏 N 个 ≈ Xk tokens」 | 计数来自 Host 侧状态，需要新增一个只读 seam（见 4.1） |
| P0 目录行上限可配 | 自己 | `catalogServers` 配置（默认 4，可到 8），超出用「+N more」；让目录行在 server 多时仍不失控 | 加长目录行会吃回一点 token，需给出默认值与测量 |
| P1 连接层懒加载 | dsh-mcp-lazy | server 级 `lazyConnect`：首次 `mcp_load`/`mcp_call` 命中才启动该 row；`warmIdleMs` 保温；面板可切换 | 启动延迟进入首调用；需要与 loader row 生命周期严格对齐，避免重复 spawn |
| P1 加载批处理提示 | 自己 + README 成本节 | `mcp_load` 支持多 name（已有）；在工具描述里明确「可以一次装载多个相关工具」；`mcp_search` 命中多个相关工具时提示合并加载 | 描述变长会抵消收益，需压到一句 |
| P2 空闲自动卸载 | 自己 | 可选 `unloadAfterIdleTurns`（默认关），仅在上下文压力大时启用 | 卸载会改变后续请求的工具数组，默认关 |
| P2 代码模式 | Anthropic | 评估：让模型写代码经 `mcp_call` 调隐藏工具（DSH 有 PTC 运行时） | 沙箱、权限、可审计性；单独设计，不在 1.x |

### 3.2 更可发现

| 项 | 吸收自 | 做法 |
|---|---|---|
| P0 空查询列 server | lazy-mcp 的树 + 我们的目录行 | `mcp_search` 传空 query 时返回 server 列表（名称、工具数、一句话、是否已加载），让模型能"先看目录再搜" |
| P0 排序与命中解释 | Anthropic 的 detail 分级 | 排序改成 name > server > description；命中行标出命中字段（`name`/`server`/`desc`），减少误判 |
| P0 同名/冲突诊断 | dsh-mcp-lazy 的准入检查 | 目录出现重名工具、来源不明、`taskSupport: required` 时，在 `mcp_search` 结果里明确标「未接管原因」，而不是静默保持可见 |
| P1 中文别名表可配 | 自己 | CJK gloss 现在是内置小表；加 `searchAliases` 配置（业务词 → server/工具名），面板可编辑 |
| P1 用法示例摘要 | lazy-mcp 的节点描述 | `mcp_search detail:"full"` 附带该工具的一条调用示例（若 MCP 提供 `examples`），没有就不编 |
| P2 分层浏览 | lazy-mcp | 目录 >N 个 server 时提供 `mcp_search server:"x"` 下钻分级（已有 server 过滤，扩展为两级：server → 工具组前缀） |

### 3.3 更可管理

| 项 | 吸收自 | 做法 |
|---|---|---|
| P0 本会话加载视图 | dsh-mcp-lazy 的会话隔离 | 面板新增「本会话已加载」区：工具名、来自哪个 server、加载轮次；`mcp_load`（无参）已能列出加载项，面板与之同源 |
| P0 隐藏原因诊断 | dsh-mcp-lazy 的 fail-open | 面板对未被接管的工具组显示原因：`alwaysVisible`、预设内挂载、重名、来源不明 |
| P0 批量操作 | 自己 | 面板支持「全部重启」「按状态筛选后批量停」；操作仍走串行队列与 409/429 语义 |
| P1 连接层开关 | dsh-mcp-lazy | 每个 server 卡上加「按需连接」开关，状态与 `lazyConnect` 配置同步（写 patch 仍需事务与校验） |
| P1 审计与回放 | 自己 | 每次 load/unload/start/stop 记一行结构化事件（谁、哪个 agent、tool 列表、耗时、结果），面板可看最近 N 条 |
| P2 策略层 | 自己 | `policy: { servers: { rea: { maxLoaded: 20 } } }` 之类的上限保护，防止模型一次 load 170 个工具把省下来的又付回去 |

## 四、怎么落到 DSH 上（适配原则）

1. **只用公开 seam。** 隐藏仍走 `agent.ctx.tools.restrict({ deny })` + 在 agent scope 重新注册；连接层走 `@deepseek-ai/dsh-mcp-client` 的 loader row（与面板同一条路径），不新造传输、不直接 kill 子进程。
2. **fail-open 优先。** 吸收 `dsh-mcp-lazy` 的准入思路：无法证明「能安全隐藏且能恢复」的工具组，一律保持原样，并在面板显示原因。
3. **版本门与探针。** 现支持 DSH 0.2.2-rc.x；0.3.0 若有 seam 变更，先加 `scripts/probe-*.mjs`（现有 `probe-live-status.mjs` 是样板），再开功能。
4. **面板不新增 RPC。** 继续用 `/dsh-mcp-hub/state|start|stop` 的既有信任校验、content-type、CAS 写 patch；新增字段只加在响应里。
5. **测量以 prompt_tokens 为准。** 字符估算只用于面板提示；对外结论一律取自 `request/header` 记录里的真实 usage 与缓存命中。
6. **不动权限边界。** 隐藏是"视图 + 派发"，`mcp_call` 仍走完整审批/超时/策略——这一点写进 README 与面板文案，不让人误以为隐藏等于禁用。

## 七、没做的事 / 待确认

- 没有在本机做严格 A/B（只在一次 profile 快照上量过工具定义 payload）；v1.5 补了一份**会话对**测量
  （`docs/v1.5-ab-measurement.md`），但同刻受控的 A/B（`prompt_tokens` + 缓存命中）仍缺。
- `dsh-mcp-lazy` 的 token 数字来自它的工具说明测量，口径与我们不同（它算「工具说明」；我们算整份工具定义 JSON），不可直接比较。
- 连接层懒加载与 1.4 的启动安全阀有交互：按需启动会频繁进入 `starting`，需要把「启动中禁用 Stop/Restart」扩展成「启动中允许取消启动」的设计讨论。

## 八、v1.5 实现偏差（2026-11-23，P0 已落地但以下不可声称）

1. **`taskSupport: required` 识别不到。** 官方 `@deepseek-ai/dsh-mcp-client` 0.2.2 的
   `createMcpToolDefinition()` 只返回 `{name, description, parameters, output, execute,
   projectContent}`，`taskRequired` 只被 `createExecutor()` 内部消费；插件拿不到该字段。因此
   task-required 工具在桥这一侧按普通工具处理，唯一信号是桥抛出的 `requires task-based
   execution` 错误。代码保留 `definition.taskRequired === true` 的 forward-compatible 检查，
   但不要在文档里把它写成「官方桥已 fail-open」。
2. **没有「加载轮次」。** 面板的 loaded view 只有每个 live agent 的已加载工具集（+ 标题/委派深度），
   没有逐次 load 的轮次、时间戳或来源 server 的独立字段（server 可从工具名解析）。
3. **未接管原因只实现三种。** 能观察到的只有 `always visible (config)`、`unrecognized name
   shape`，以及桥暴露 `taskRequired` 时的 `task support required`。重名、来源不明、预设内挂载
   在全局 registry 里不可见，做不到；不要把它们写进已支持列表。
4. **server 名含 `__` 的解析边界。** 公开名 `mcp__<server>__<tool>` 按第一个 `__` 解析；`SERVER_NAME_PATTERN`
   允许下划线，所以 `my__server` 会被归到 `my`。这是既有命名契约「public name 不用于反解」的
   已知边界，面板与 footprint 的 per-server 分桶在极端命名下会不准。
5. **A/B 不是同刻受控。** 本轮是会话对测量（不同日期/DSH 构建/历史），不是 §五 要求的同 profile
   同 MCP 集合、同刻开关的受控 A/B；也没有抓 provider 的 `prompt_tokens` 与缓存命中。
6. **发布历史。** 这些改动未单独发布为 v1.5，后续纳入 GitHub v1.6.0。

## 九、P1 连接层懒加载（2026-11-23，工作树，未发布）

- **语义（P1.1 自动接管）**：`lazyConnect: ['*']` 接管所有 `dsh-mcp-client` 行，包括后来新增的。
  启动或新增时正在运行/启动中的行会被观察 `autoPrimeMs`（默认 15000），写缓存后**自动停一次**；
  删除的行由扫描器从缓存里清掉，所以新增/卸载不需要人工启停。工具元数据从
  `<profile>/mcp-progressive/tool-cache.json` 读（只存 `name`/`description`/`parameters`，
  不存 env/密钥），`mcp_search` 用 `[lazy]` 标出；第一次 `mcp_load`/`mcp_call` 命中缓存工具时，
  管理半的 `ensureServer` 串行启动该行并等工具注册，然后走 live definition；失败原因原样回给模型。
  扫描器只观察 `serverControl.listServers()`，从不主动启动新行。
- **保温**：`warmIdleMs`（默认 600000，0=不自动停）在最后一次活动后释放；有已加载工具、或有
  调用在飞时会抑制计时器（已发出的 release 不会被取消）；`mcp_load unload:true` 后会重新计时。`lazyStartTimeoutMs` 默认 30000（5–120 秒）。
- **与提案的偏差**：① 面板只显示 `lazy` 标记，**没有**做 `lazyConnect` 开关（改配置仍是补丁编辑）；
  ② 缓存是快照，工具列表变了要等下一次非空连接刷新；③ server 名含 `__` 的解析边界仍存在；
  ④ 新增时已经 `disabled: true` 的行没有工具可观察，第一次按需启动前没有缓存（唯一需要先启动的
  边界）；⑤ 自定义 MCP 插件（如 `openmotion`）不是 `dsh-mcp-client` 行，管理半看不到也停不了它的
  进程；⑥ 没有做同刻缓存 A/B（`warmIdleMs`/auto-prime 的收益与代价未量化）。
- **证据（同一快照）**：`npm test` 302（299 pass / 3 skip）；CI 260/42；`live-boot` 13/13；
  `probe-live-status` 8/8；`repro-review` 0/6；`measure --self-test` 21。管理测试覆盖
  disabled→started、already-running、not-lazy、unknown、timeout、并发只 toggle 一次、in-use /
  starting 拒绝；core 测试覆盖缓存读写/合并、`[lazy]` 搜索、缓存工具 `mcp_load`/`mcp_call` 启动、
  timeout 原因、warm timer 与 loaded/unload 交互。没有真机 lazy 面板点按验收。2026-11-24 00:53 的进程与工具定义检查（一个 `mcp_call`，无 `mcp_load`）见
  `docs/v1.6-p1-cost.md`：prompt 工具定义 55 tools / 18,101 tokens 前后 Δ0；rea 停止时进程 0 KB，
  lazy 启动 4.388 s，启动后 RSS 417,040 KB；10 min 保温后（01:04:47）进程已消失、`mcp_servers` 回到 `stopped, lazy`。
- **已知边界**：① CI 姿态跳过所有 Host 侧 lazy 用例（`runtimeTest`），只跑 `toolcache` +
  management；真实 Loader 的 `state-lazy-row` 只证明 `lazyConnect` 接线 + 缓存读取，不启动
  lazy 行；② 懒 server 重连后若变成 0 个工具，缓存 bucket 不会被清空（无法区分「未连接」与
  「零工具」），旧 `[lazy]` 条目会留到下次有工具时刷新；③ 同刻缓存收益/`warmIdleMs` 代价未量化；
  ④ auto-prime 会在启动/新增时让每个运行中的 client 行先跑一次（最长 15 s）再停，存在一次
  process spike，不是“启动即零进程”；⑤ 自定义 MCP 插件（openmotion）仍常驻。
